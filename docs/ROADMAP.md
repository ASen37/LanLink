# LanLink 未来调整方向

> 这里记录**已明确暂缓**或**评估后暂不实施**的功能，作为后续迭代的参考，不代表承诺或排期。
> 当前已实现的能力见 [README](../README.md) 与 [使用文档](USAGE.md)。

## 优先级一览

| 优先级 | 方向 | 主要风险 |
| --- | --- | --- |
| P1 | 访客上传总配额 | 误伤合法大批量上传 |
| P2 | 访客文件夹打包下载 | ZIP64 / 大目录压力 |
| P3 | 访客直接写入指定文件夹（HTTPS） | 证书警告影响零安装体验 |
| P4 | 下载增强（多共享根 / 限速 / 日志） | 需求优先级低 |
| P5 | 多 TCP 通道传输（暂缓，待千兆环境复测） | 复杂度高，当前收益仅 10–15% |
| P6 | 多设备并发传输（待评估） | 需要全局调度，收益依场景 |

---

## 1. 访客上传总配额（P1）

**背景**

目前 `guestMaxFileMB` / `guestMaxBatchMB` 只限制**单个文件**和**单批任务**。在链接有效期内、主机保持在线时，访客可以反复新建批次，累计上传量没有上限。

**现状**

- 单文件、单批有限制
- 累计接收字节数、文件数没有统计与上限
- 链接到期或主机重启才会自然中断

**建议方案**

- 每次开启访客模式时重置配额计数
- 记录本次开启期间累计接收的字节数与文件数
- 超过阈值后拒绝新批次/新分块，并返回明确的错误提示
- 设置页展示“已用 / 上限”，支持“提高配额”或“立即重置”
- 可选：按访客 IP 分别统计，避免单一访客占满


**风险**：合法的批量上传可能被误伤，需要显眼的配额提示和放行入口。

---

## 2. 访客文件夹打包下载（P2，暂缓）

**背景**

当前访客下载只支持单个文件；共享的是文件夹时，需要逐层进入后逐个下载。

**技术难点**

项目坚持**零运行时依赖**，没有 `archiver` / `yazl`，需要手写 ZIP 写入器：

- CRC32 表 + 本地文件头 + 中央目录，约 150 行
- 超过 4 GB 的文件夹需要 ZIP64，再增加 150–250 行
- 流式输出时无法预知总大小，要用 data descriptor 或先扫一遍目录

**可选方案**

1. 手写流式 ZIP（store 模式优先，保速度；文本可选 deflate）
2. 引入 `archiver` 依赖（ZIP 部分工作量明显减少，但破坏零依赖）
3. 先只支持 4 GB 以内，ZIP64 二期再加


**风险**：ZIP64 偏移/描述符容易出错；大目录打包会打满磁盘与 CPU，需要并发限制。

## 3. 访客直接写入指定文件夹（P3，暂缓）

**背景**

现在访客点“下载”走浏览器原生下载，只能落到浏览器默认下载目录，不能直接写入访客自己指定的文件夹。

**浏览器限制（已实测）**

| 场景 | `isSecureContext` | `showDirectoryPicker` |
| --- | --- | --- |
| 访客页（`http://192.168.x.x:7450`） | `false` | `undefined` |
| 自签 HTTPS 页（点“继续前往”后） | `true` | `function` |

普通 HTTP 页面不具备安全上下文，浏览器不允许网页直接写磁盘。

**可行方案**

1. 访客模式增加 HTTPS 监听（自签证书）
2. 访客首次访问点一次“高级 → 继续前往”
3. 下载页提供“保存到文件夹”，用 File System Access API 流式写入并显示进度
4. Firefox / Safari 等不支持的环境自动回退为浏览器下载

**证书生成选项**

- 调用系统 `openssl`（不保证每台机器都有）
- 手写极简 X.509 自签生成器（零依赖，约 200 行）
- 引入 `selfsigned` 依赖（破坏零依赖）


**风险**：证书警告会削弱“访客零安装”的体验；即使做了，访客也必须手动选择一次文件夹。

---

## 4. 下载增强（P4）

- **多共享根目录**：当前只支持一个共享文件/文件夹
- **下载限速与并发上限**：避免多个访客同时拉满带宽/磁盘
- **下载日志**：记录谁在何时下载了哪些文件（可选写入历史页）
- **断点续传**：HTTP `Range` 已支持，可在 UI 上补充进度与重试提示
- **共享目录只读确认**：首次选择目录时二次确认，降低误共享风险

## 5. 多 TCP 通道传输（P5，暂缓）

**背景**

当前每对设备只建立 **1 条 TCP** 连接传文件，但发送端有 `WINDOW = 8` 个分块在途的流水线，并不是“一问一答”。Node 是单线程事件循环，没有 worker 线程，AES-GCM 与 SHA-256 都在主线程完成。

**实测数据（2026-10-30，百兆局域网，iperf3 3.22）**

| 测试 | 总吞吐 | 折合 |
| --- | --- | --- |
| `-P 1` 单流 | 65.2 Mbps | ≈ 8.1 MB/s |
| `-P 4` 四流 | 93.0 Mbps | ≈ 11.6 MB/s |
| `-P 8` 八流 | 93.9 Mbps | ≈ 11.7 MB/s |

**分析**

- `-P 4` 与 `-P 8` 都卡在 93–94 Mbps，说明链路是 **百兆以太网**（或等效百兆的 Wi-Fi），已经到顶
- 单流只跑到链路上限的 **69%**，多流能把空口/队列填满，网络层提升约 **+43%**
- 但 LanLink 实际传文件约 **10 MB/s ≈ 80 Mbps**，已经介于单流与多流之间，现有 8 分块流水线弥补了一部分
- 因此改多通道预计只能带来 **10–15%** 的提升，绝对速度仍被锁在 ~11.6 MB/s

**触发条件（满足再考虑）**

1. 两端升级到千兆（或 5GHz Wi-Fi 实测 >300 Mbps）
2. 复测 `-P 1` 仍明显低于链路上限（例如千兆下单流只有 300–500 Mbps）
3. 且 `-P 4` 相比 `-P 1` 有明显叠加

**方案要点**

- 会话多路复用：连接 id、分块分配到不同连接、接收端乱序重组与统一 ack
- 每条连接独立的加密 nonce 域，避免 GCM nonce 复用
- 单连接断开后的重连与缺失分块续传
- 接收端并发写盘（分片写或独立临时文件）
- 可选的轻量优化：增大 `WINDOW`、SHA-256/加密移入 worker 线程、调整 `UV_THREADPOOL_SIZE`

**复杂度**：较高，会显著增加传输状态机复杂度。

**结论**：暂缓。当前瓶颈是百兆链路，升级网络比改代码收益高一个数量级。

## 6. 多设备并发传输（P6，待评估）

**背景**

LanLink 每对设备建立一条独立的 TCP 会话，同一会话同时只允许一个传输任务；**不同设备之间目前没有全局并发限制**，多台设备可以同时互传。访客上传每个访客还有 3 个并发分块请求，多个访客会进一步叠加连接数。

**性能影响因素**

| 场景 | 影响 |
| --- | --- |
| 多对设备接在同一台非阻塞千兆交换机 | 影响较小，交换机内部可并行转发 |
| 多对设备共享同一个路由器上联口 / 同一根网线 | 总带宽被平分，影响明显 |
| Wi-Fi | 空口共享，设备越多每台越慢，还有竞争与重传 |
| 同一台电脑同时收发多路 | 网卡、磁盘、CPU 共享，机械硬盘尤其明显 |
| 百兆网络 | 无论几对，总和很难超过约 94 Mbps |

**现状与问题**

- 没有全局并发上限、队列或总带宽限制
- 多设备同时传输时，快慢完全由操作系统调度和硬件决定
- 访客批次与设备互传之间也没有优先级区分
- 单设备对多设备发送时，磁盘读取与加密会互相争抢 CPU
- 同名文件并发：设备互传已用“目标路径租约 + 自动改名”解决；访客上传遇到同名并发仍返回“正在处理”

**建议方向**

1. 可配置的**全局并发传输数**（例如同时最多 2 路）
2. 可选的**总带宽上限**，避免多设备把链路打满
3. 发送队列与公平调度（设备之间轮转，避免大文件饿死小文件）
4. 访客上传与设备互传分优先级
5. 在传输页展示当前并发与总速度

**测试方法**

- 用 iperf3 开多对并行流，观察总吞吐与单对流吞吐
- 或同时发起两个 LanLink 传输，对比单任务与双任务的总速度
- 有线与 Wi-Fi 分别测一次

**复杂度**：并发上限较低；完整队列与限速更高。

**状态**：待评估，先记录现象与方案，暂不实施。

## 7. 其他已知限制（来自 README）

- 安装包未做代码签名，首次运行可能触发 SmartScreen
- 没有自动更新、二维码、手机 App、开机自启
- 界面暂无“解除配对”入口，需要断开或手工编辑 `trusted.json`
- UDP 组播发现不跨路由器，跨网段需手动连接 IP
- 访客模式是 HTTP 明文，仅建议在可信局域网使用
